# INC-2026-003 — Order Retrieval API Timeout

## Incident Summary

A customer was unable to retrieve order `5005` through the Order API.

The initial request returned `401 Unauthorized` because authentication credentials were missing. After supplying a valid bearer token, the request progressed further but returned `504 Gateway Timeout`.

Application logs showed that the backend successfully authenticated the user but the database query for order `5005` took approximately 40–50 seconds before timing out.

Database monitoring showed high CPU utilization, near-maximum connection usage, and multiple long-running queries.

The evidence strongly indicates a **database performance/resource contention issue**, although the exact root cause was not conclusively established during the investigation.

---

## Customer Impact

**Affected functionality:** Order retrieval

**Affected resource:** Order `5005`

**Customer impact:** Customer unable to view the order through the application/API.

**Severity:** High — customer-facing functionality is failing for the affected request.

---

## Initial Request

The reported request was:

```bash
curl -i https://api.shop.example.com/api/orders/5005
```

Response:

```text
HTTP/2 401 Unauthorized
```

Response body:

```json
{
  "error": "Authentication required"
}
```

### Initial Assessment

The request did not include the authentication credentials required by the API.

This was an authentication issue rather than evidence of an application, database, or network failure.

---

## Authentication Retry

The API documentation specifies bearer-token authentication.

The request was retried with a valid token:

```bash
curl -i \
  -H "Authorization: Bearer <token>" \
  -H "Accept: application/json" \
  https://api.shop.example.com/api/orders/5005
```

The response changed to:

```text
HTTP/2 504 Gateway Timeout
```

Response:

```json
{
  "error": "Upstream service timeout"
}
```

### Assessment

Authentication was successful.

The request therefore progressed beyond the authentication stage and encountered a downstream/upstream timeout.

---

## Application Log Investigation

Application logs were searched using the request ID and order ID.

Relevant logs:

```text
2026-10-03 14:32:11 INFO GET /api/orders/5005 request_id=REQ-9821
2026-10-03 14:32:11 INFO Authentication successful user_id=721
2026-10-03 14:32:11 INFO Fetching order order_id=5005
2026-10-03 14:32:11 INFO Database query started request_id=REQ-9821
2026-10-03 14:32:56 ERROR Database query timeout request_id=REQ-9821
2026-10-03 14:32:56 ERROR Failed to fetch order order_id=5005
2026-10-03 14:32:56 ERROR Upstream dependency timeout
```

### Findings

The logs establish the following sequence:

```text
API request
    ↓
Authentication successful
    ↓
Order lookup started
    ↓
Database query started
    ↓
Database query timed out
    ↓
Order retrieval failed
    ↓
API returned 504
```

This provides strong evidence that the timeout occurred while the application was waiting for the database operation.

---

## Database Connectivity Check

A TCP connectivity test was performed against the database:

```bash
nc -vz db-prod-01 5432
```

Result:

```text
connection succeeded
```

### Assessment

Basic TCP connectivity to the PostgreSQL database was successful.

Therefore, there is no evidence of a basic network connectivity failure between the application environment and the database.

This does **not** prove that the database is healthy. A database can be reachable while still experiencing severe performance problems.

---

## Database Query Investigation

The relevant query was:

```sql
SELECT *
FROM orders
WHERE order_id = 5005;
```

Under normal conditions, the query completes in:

```text
<100 ms
```

During the incident, the query took approximately:

```text
40–50 seconds
```

This is a significant increase in query latency.

---

## Database Monitoring Findings

Database monitoring showed:

```text
CPU utilization:       94%
Active connections:    198 / 200
Long-running queries:  17
```

These metrics indicate significant database resource utilization.

### Interpretation

The combination of:

- Very high CPU utilization
- Almost exhausted connection capacity
- Multiple long-running queries
- Dramatically increased query latency
- Application-side database timeout

provides strong evidence of database performance/resource contention.

## Assessment

### Confirmed

The following facts are confirmed:

1. The customer request reached the API.
2. Authentication succeeded after valid credentials were supplied.
3. The API returned `504 Gateway Timeout`.
4. The application logged a database query timeout.
5. Database TCP connectivity was successful.
6. The affected query normally completes in under 100 ms.
7. The query took approximately 40–50 seconds during the incident.
8. Database CPU utilization was 94%.
9. 198 of 200 database connections were active.
10. 17 long-running queries were present.

### Likely Cause

The evidence strongly indicates **database performance/resource contention** as the cause of the API timeout.

### Not Yet Confirmed

The exact underlying database cause has not been established.

Possible areas requiring further investigation include:

- Long-running queries
- Query execution plans
- Missing or ineffective indexes
- Lock contention
- Connection pool saturation
- Database workload
- Recent application/database changes
- Resource-intensive queries

## Support Lesson

A strong support investigation does not require immediately fixing the underlying problem.

The goal is to:

1. Reproduce the issue.
2. Determine where the request fails.
3. Gather objective evidence.
4. Eliminate unsupported hypotheses.
5. Identify the most likely failing component.
6. Clearly distinguish confirmed facts from assumptions.
7. Escalate with enough technical information for the next team to continue the investigation.
